# Подключение арендатора: механизм заведения и первый вход (Окно 69)

Дата: 26.08.2026 · Размер: L · Скилл: `вайбкодинг`
Первый, кто через это проходит: клиника Карины Урбашевичус.

---

## Problem

Этап A запер данные арендаторов замком в базе, Этап B научил кабинет говорить словами
вертикали. Оба на проде. Критерий приёмки 6 спеки Этапа A обещал: «второй арендатор
подключается за минуты - строка в справочнике плюс домен, без правок кода и без новой
миграции». Проверка 26.08.2026 показала, что записать эту строку **нечем**:

1. **База недоступна снаружи.** `DB_HOST` - внутреннее имя кластера Amvera, ни `psql`,
   ни `pg_dump` с машины Влада не резолвят его вовсе (та же причина, по которой копия
   базы снимается роутом `/backup`, а не дампом).
2. **Роута заведения арендатора не существует.** Проверено по реестру `ROUTES` в
   `api/server.mjs` - ни `POST /tenants`, ни чего-либо близкого.
3. **Миграции - только про схему** (правило проекта, инцидент 04.08.2026). Строка
   Алихана в `057_tenants.sql` была единственным осознанным исключением.
4. **Замкнутый круг первого владельца.** `POST /staff` требует роль management **того
   же арендатора** (`canManageStaff`, реестр `auth: 'management'`). У нового арендатора
   сотрудников нет вообще - создать первого владельца некому.

Живая улика состояния на 26.08.2026 (запрос с моей машины):

```
GET /health, Origin: vladislaavkozlov.github.io   → 200
GET /tenant/appearance, Origin: vladislaavkozlov.github.io → 200, vertical=barbershop
GET /tenant/appearance, Origin: karinaurbashevichus.ru     → 404 {"error":"unknown_tenant"}
```

То есть арендатора Карины нет, и аварийная ручка `TENANT_FALLBACK_ID` выключена
(иначе её домен обслуживал бы Алихан).

## Goal

Сделать подключение арендатора **выполнимой и повторяемой операцией**, а не разовым
подвигом. Заведение Карины - первое применение механизма, а не его цель.

## Scope

1. Механизм заведения арендатора и его первого владельца на живой базе.
2. Первый вход владельца по временному PIN и штатная его смена.
3. Описанный контур фронта Карины и защита от разъезда версий кабинетов.
4. Минимальное наполнение клиники: владелец + две процедуры.
5. Честная проверка: пройдёт ли Карина путь «добавить сотрудника, процедуру, график»
   одна, без разработчика.

## Non-Goals

- орто-модули (план лечения, рассрочка, зубная формула) - Этап D;
- темы оформления под её бренд (логотип, заголовок вкладки, превью) - Этап D;
- права ролей - полномочия общие для всех арендаторов (решение Влада 24.08.2026);
- словарь и флаги вертикали - на проде, работают, не переделываются;
- поток живых событий - ждёт ответа поддержки Amvera.

## Решение: заведение при старте приложения из переменной окружения (вариант D)

Влад задаёт в панели Amvera переменную `NEW_TENANT`, перезапускает приложение -
арендатор и его первый владелец созданы, в лог ушла одна строка подтверждения,
переменную можно убрать.

### Почему именно так

| | Подход | Вердикт |
|---|---|---|
| **A** | Закрытый роут `POST /tenants` по образцу `/backup` | Запасной. Работает без перезапуска, но открывает наружу новую дверь на самом чувствительном месте: роут, заводящий владельцев, - цель не менее лакомая, чем роут, отдающий базу |
| **B** | Скрипт внутри контейнера Amvera | Отклонён: требует доступа к консоли контейнера, которого у нас нет и который решение не должно требовать (решение Влада 26.08.2026) |
| **C** | Миграция-исключение | Отклонён: данные в миграциях запрещены правилом проекта; каждый клиент = новая миграция |
| **D** | Переменная окружения при старте | **Выбран** |

Обоснование D:
- **наружу не открывается ничего** - ни одного нового HTTP-роута;
- **механизм уже освоен Владом**: ровно так работают `LIVE_EVENTS`, `BACKUP_TOKEN`,
  `TENANT_FALLBACK_ID`, `DB_POOL_MAX`;
- **это индустриальный образец, а не изобретение**: Keycloak заводит первого
  администратора переменными `KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD`
  при старте сервера, и там же явно требует идемпотентности (повторный старт не
  пересоздаёт учётку);
- **идемпотентность дёшева**: домен арендатора уже уникален по смыслу, повторный старт
  находит существующего и не трогает ни строки;
- **цена** записана честно: заведение требует перезапуска, а сгенерированный временный
  PIN попадает в лог приложения. Второе снимается тем, что PIN можно **задать** в самой
  переменной - тогда в лог не уходит ничего секретного.

### Контракт переменной `NEW_TENANT`

Одна переменная, значение - JSON. Одним блоком, а не набором плоских переменных:
вложенность (владелец, список процедур) в плоском виде склеивается строками и это
ровно тот класс опечатки, который здесь недопустим.

```json
{
  "name": "Урбашевичус - клиника авторской ортодонтии",
  "domains": ["crm.karinaurbashevichus.ru"],
  "vertical": "clinic",
  "owner": { "name": "Карина Урбашевичус", "email": "karina@...", "pin": "482913" },
  "services": [
    { "name": "Консультация", "durationMin": 30, "price": 0 },
    { "name": "Повторный сеанс", "durationMin": 30, "price": 0 }
  ]
}
```

- `owner.pin` необязателен. Задан - в лог не уходит; не задан - генерируется и
  печатается в лог ровно один раз;
- `modules` необязателен. У Карины не задаётся: оба флага остаются включёнными
  (решение Влада), а это и есть умолчание вертикали;
- незнакомые ключи - ошибка, а не «пропустим молча»: тихо проигнорированный ключ
  означает, что человек думает, будто задал одно, а получил другое.

### Что происходит при старте

Одна транзакция в служебном контексте (`SYSTEM_TENANT`), после миграций, до `listen`:

1. по каждому домену ищется существующий арендатор. Найден - **выход без единой
   записи**, в лог «арендатор уже подключён, id=N, ничего не менялось». PIN не
   сбрасывается, имя не переписывается;
2. строка в `tenants` (имя, домены, вертикаль, флаги);
3. владелец в `staff`: роль `owner`, `must_change_pin = true`, `protected_owner = true`,
   `tenant_id` **проставляется явно** (умолчание колонки - `current_setting('app.tenant_id')`,
   а в служебном контексте там `'*'`, и вставка без явного значения упала бы);
4. две процедуры в `services` и их привязка к владельцу в `master_services`;
5. одна строка в лог.

Ошибка на любом шаге - откат целиком, половины арендатора не остаётся.

### Что делать с ошибкой в самой переменной

Битый JSON, отсутствующая почта, домен с кириллицей - **сервер стартует**, громко
пишет ошибку в лог и не заводит никого. Ронять живой салон Алихана из-за опечатки в
переменной, относящейся к другому клиенту, недопустимо. Это не противоречит требованию
fail-closed: оно про атомарность заведения, а не про доступность приложения.

Опечатку ловим **до** перезапуска: `tools/check-new-tenant.mjs` печатает, что именно
будет создано, и не пишет в базу ни строки.

### Как разрывается замкнутый круг первого владельца

Явно и в одном месте: первый владелец создаётся тем же служебным механизмом, что и сам
арендатор, при старте приложения. Права `POST /staff` **не ослабляются** - создание
сотрудника снаружи по-прежнему требует management того же арендатора.

## Первый вход Карины

Второй механизм не заводится, используется существующий:

1. `POST /auth/login` с почтой и временным PIN → в ответе `mustChangePin: true`;
2. кабинет показывает баннер временного PIN;
3. `PUT /staff/:id/pin` (реестр: `auth: 'owner'`) - она сама владелец, значит меняет
   PIN себе. `must_change_pin` гасится этой же операцией.

Ограничение, принятое осознанно: `protected_owner = true` защищает её от разжалования и
увольнения (замок последнего владельца), но той же ценой закрывает **редактирование её
карточки** - `canMutateProtectedOwner` возвращает false всем. Ровно так живёт Алиовсад у
Алихана. Следуем существующему шаблону; смена PIN этим не затронута.

## Контур фронта Карины

Факты на 26.08.2026:

- `karinaurbashevichus.ru` отвечает 200, A-запись `158.160.116.199` - **не Amvera**;
- поддомена `crm.karinaurbashevichus.ru` в DNS нет;
- кабинет узнаёт арендатора по `Origin`, значит открыть кабинет Алихана Карина не
  может физически - её домен обязан быть в её строке справочника.

Решение: кабинет Карины живёт на **поддомене** `crm.karinaurbashevichus.ru`, статика -
её приложение на Amvera. Основной сайт клиники не трогается.

Контуров фронта становится два: Алихан на GitHub Pages, Карина на Amvera. Опасность -
не в самой выкладке, а в том, что через месяц у клиентов разные версии одного экрана и
баг у одного невоспроизводим у другого.

Защита - **детектор, а не дисциплина**: прогон `tools/verify-2026-08-26-front-parity.mjs`
скачивает `crm-owner.html`, `crm-admin.html`, `crm-master.html` и их `assets/*` с обоих
доменов и сравнивает хэши. Разъехались - прогон красный, с именами разошедшихся файлов.
Правки в коде кабинета это не требует.

## Acceptance Criteria

1. **Арендатор заводится механизмом, не руками.** Живой прогон на настоящем Postgres:
   старт с `NEW_TENANT` создаёт арендатора, владельца и две процедуры; в базе ровно эти
   строки и ни одной лишней.
2. **Повторяемость.** Тот же способ заводит третьего арендатора без единой правки кода.
3. **Идемпотентность.** Второй старт с той же переменной не создаёт второго Карину, не
   сбрасывает PIN, не переписывает имя. Проверяется автотестом, который падает при
   снятии проверки существующего домена.
4. **Fail-closed.** Ошибка на любом шаге заведения - в базе не появилось ничего.
   Проверяется искусственным сбоем на последнем шаге.
5. **Опечатка не роняет Алихана.** Старт с битым `NEW_TENANT`: сервер поднялся, Алихан
   отвечает как прежде, в логе явная ошибка, в базе пусто.
6. **Первый вход работает.** Карина входит по почте и временному PIN, получает
   `mustChangePin`, меняет PIN, входит новым.
7. **Изоляция после заведения доказана атакой.** `tools/verify-2026-08-24-tenant-rls.mjs`
   зелёный; учётка Карины не возвращает ни одной строки Алихана ни на одном роуте.
8. **Алихан не заметил.** `DUMP_TEXT=... node tools/verify-2026-08-24-tenant-cabinets.mjs`
   на текущем коммите и на новом - различий строк ноль. Офлайн-набор (база отсчёта -
   **715 тестов, все зелёные, прогон 26.08.2026**) не уронен.
9. **Кабинет Карины говорит её словами** - живой прогон в браузере на двух арендаторах.
10. **Путь Карины пройден свежим глазом**: добавить сотрудника, завести процедуру,
    поставить график - что из этого она может одна, записано честно (см. находки).

## Находки исследования, меняющие обещание клиенту

Проверено по реестру `ROUTES` и по фронту, это факты, а не опасения:

1. **Завести процедуру из кабинета нельзя.** `POST /services` не существует - в реестре
   только `GET /services`, `GET /master-services`, `PUT /master-services/:masterId/:serviceId`.
   Каталог процедур у Алихана приехал сидом миграции `002_schema.sql`. Значит фраза
   «настоящий прайс Карина заведёт позже сама» **сегодня неисполнима**: она может
   поменять цену и длительность процедуры под конкретного врача, но не добавить новую
   строку в каталог. Это отдельное окно (CRUD каталога), не это.
2. **Завести точку из кабинета нельзя** - `POST /locations` не существует. Практического
   вреда для клиники не нашли: карточка сотрудника шлёт `locationId: value || null`,
   пустой список даёт `null`, а колонка это допускает.
3. **Сотрудника и график Карина заводит сама** - `POST /staff` и `PUT /master-weekly-schedule`
   в реестре есть, роль владельца их проходит. Подтверждается живым прогоном её кабинета,
   а не только чтением реестра.

## Явные допущения (проверить на гейте, не выдуманы молча)

- **Карина принимает пациентов сама**: `provides_services = true`, обе процедуры
  привязываются к ней в `master_services`. Иначе её кабинет встретит её расписанием без
  единого врача.
- **Цена и длительность процедур на старте - заглушки** (0 руб., 30 минут): настоящих
  цифр у нас нет и выдумывать их нельзя. Поправить их под себя она может из кабинета
  (`PUT /master-services/...`), в отличие от добавления новых строк каталога.
- **Домен кабинета - `crm.karinaurbashevichus.ru`** (подтверждено Владом), основной
  сайт не трогается.
- **Карина принимает пациентов сама** - подтверждено Владом.
- **Каталог процедур (находка 1) - отдельным окном после запуска** - решение Влада.
- **Логин Карины - `karina@urbashevichus.ru`** (решение Влада 26.08.2026, дословно).
  Почта в этой системе - только логин: отправки писем в проекте нет вовсе (ни SMTP,
  ни внешнего сервиса), проверяется одной регуляркой, а боевые логины Алихана живут
  на несуществующем домене `.test`. Отмечено и не считается ошибкой: домен логина
  (`urbashevichus.ru`) короче домена её сайта (`karinaurbashevichus.ru`) - на вход это
  не влияет никак, ключ входа составной `(tenant_id, email)`.

## Constraints

- прод живой у Алихана: реальные записи, реальные деньги. Деплой - только по явной
  команде Влада, перед любой правкой боевых данных - свежая копия (`tools/backup-prod.mjs`);
- внешних зависимостей у API нет и не появляется (только `pg`);
- поведение и контракты существующих роутов не меняются;
- **`BACKUP_TOKEN` Влад удалил из панели 26.08.2026.** Доказать, что роут закрыт,
  сегодня нечем: без настоящего секрета выключенный роут и неверный секрет отвечают
  одинаково (404), а признака перезапуска процесса в `/health` нет. Закроется по
  построению при перезапуске контейнера на деплое этого окна (фаза 6). Чтобы такой
  вопрос больше не был недоказуемым, `/health` получает время старта процесса;
- переменные окружения на Amvera применяются **только при перезапуске приложения**
  (найдено живьём 26.08.2026 на `BACKUP_TOKEN`: переменная убрана из панели, а
  работающий контейнер продолжал отдавать базу на прежний секрет).
