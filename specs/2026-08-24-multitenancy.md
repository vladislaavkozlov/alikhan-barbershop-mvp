# Мультиарендность, Этап A: изоляция арендаторов

Дата: 24.08.2026 · Размер: L · Статус: спека, к реализации не приступали

## Problem

CRM написана под одного заказчика (барбершоп «Алихан»). В базе нет ни одного признака
«чей это»: 14 таблиц, ~222 места с SQL, и любой запрос видит все строки. Подключить
второго клиента (ортодонт Карина, своя клиника, оплатила сайт 24.08.2026) сейчас
физически нельзя - она увидела бы записи, клиентов и деньги Алихана.

Переделка дорожает нелинейно: сегодня в базе один арендатор и перенос данных
тривиален, на десяти клиентах это месяц работы с риском перепутать чужие данные.

## Goal

Одно ядро обслуживает несколько независимых бизнесов. Данные арендатора не покидают
его периметр ни при какой ошибке в коде приложения. Алихан продолжает работать, не
заметив изменений.

## Scope (Этап A)

- Справочник арендаторов и признак принадлежности во всех таблицах
- Изоляция, обеспеченная самой базой (RLS), а не аккуратностью в коде
- Определение арендатора по домену запроса, включая CORS
- Алихан переезжает как арендатор №1
- Подключение второго арендатора = вставка строки в справочник

## Non-Goals (сюда НЕ входит, отдельные этапы)

- Словарь терминов вертикали («мастер»/«врач») - Этап B
- Флаги модулей по вертикалям - Этап B
- Темы оформления под сайт клиента - Этап D
- Биллинг, приём карт, самостоятельная регистрация - позже
- Отдельная база под ВИП и контур 152-ФЗ - позже (архитектура это уже допускает)
- Орто-модули (план лечения, рассрочка, зубная формула) - Этап D

## Acceptance Criteria

1. **Изоляция доказана атакой, а не рассуждением.** Тестовый арендатор №2 с данными;
   живой прогон под учёткой №2 через API не возвращает ни одной строки арендатора №1
   ни на одном роуте. Проверяется автотестом, который падает при отключении RLS.
2. **Изоляция работает при ошибке в коде.** Запрос без единого условия
   (`SELECT * FROM bookings`) из-под арендатора №2 возвращает только его строки.
3. **Нет утечки между запросами через пул.** Тест: подряд идущие запросы разных
   арендаторов на одном соединении не видят чужой контекст.
4. **Запрос без арендатора не проходит.** Неизвестный домен → 404, а не данные Алихана.
5. **Алихан не заметил изменений.** Полный офлайн-набор тестов зелёный; живой
   CDP-прогон трёх кабинетов (владелец / администратор / мастер) - поведение как до.
6. **Второй арендатор подключается за минуты** - строка в справочнике плюс домен,
   без правок кода и без новой миграции.
7. **Откат возможен.** Репетиция на копии боевой базы пройдена, путь отката записан
   и проверен до переключения прода.

## Constraints

- **Прод живой.** Реальный салон, реальные записи, деньги. Простой согласуется с
  Алиханом заранее, деплой - только по явной команде Влада
- Внешних зависимостей у API нет и не появляется (только `pg`)
- Поведение и контракты API не меняются - это перенос, не переписывание
- Одноразовые QA-фикстуры не живут в миграциях (инцидент 04.08.2026)

## Известные ловушки (найдены исследованием 24.08.2026, не гипотезы)

1. **Владелец таблиц обходит RLS молча.** `ENABLE ROW LEVEL SECURITY` без `FORCE` не
   действует на владельца таблиц, а приложение на Amvera подключается именно тем
   пользователем, который таблицы и создал. Тестирование «изоляция работает» дало бы
   ложноположительный результат. Обязателен `FORCE ROW LEVEL SECURITY`.
2. **Пул соединений протекает контекстом.** Обычный `SET` живёт до конца соединения и
   уезжает в следующий запрос другого арендатора. Обязателен `SET LOCAL` внутри
   транзакции.
3. **Долгоживущие соединения несовместимы с транзакцией на запрос.** Поток живых
   событий (`api/lib/events.js`, SSE) держит ответ открытым бесконечно - обёрнутый в
   транзакцию, он выест пул. Такие роуты определяют арендатора и сразу отпускают
   соединение.
4. **Одиночные строки настроек ломаются.** `payroll_settings` (`id integer primary key
   default 1`) и `discount_settings` (`id boolean primary key default true`) физически
   допускают одну строку на всю систему. Становятся строкой на арендатора.
5. **Глобальные уникальные ключи ломаются.** `staff.email`, `clients(phone)`,
   `holidays.date` (первичный ключ!), `staff_one_protected_owner_idx`, dedup-индексы
   уведомлений - все становятся составными с арендатором.
6. **Индекс без арендатора впереди** замедляет выборки на два порядка.
7. **CORS настроен одним доменом** (`ALLOWED_ORIGIN`) - при домене на арендатора
   список разрешённых источников берётся из справочника.
8. **Вход ищет сотрудника по всей базе** (`WHERE email = $1`) - два клиента с
   одинаковой почтой сломают вход друг другу.

## Что НЕ является риском (проверено)

- Текстовые id (`staff-<32 hex>`) генерируются случайно, столкновений между
  арендаторами не будет. Исторические `master-1` существуют только у Алихана
  и приехали из миграций - правило «миграции только про схему» это и закрывает.
