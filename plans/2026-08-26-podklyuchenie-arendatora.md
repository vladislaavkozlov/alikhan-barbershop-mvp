## Фаза 1. Разбор и проверка переменной, без базы

**Файл:** `api/lib/provision-tenant.js` (новый) - только чистые функции.

- `parseTenantSpec(raw)`: JSON → нормализованная заявка либо понятная ошибка.
  Проверяет: непустое имя; хотя бы один домен, каждый прогнан через `normalizeDomain`
  и совпал с исходным (кириллица, пробел, слэш - отказ); вертикаль из известных
  (`MODULE_DEFAULTS`); почта владельца через существующий `normalizeEmail`; PIN, если
  задан, через существующий `isValidPin`; процедуры - непустое имя, целые
  `durationMin > 0` и `price >= 0`; незнакомый ключ верхнего уровня - отказ.
- `describeTenantSpec(spec)`: человекочитаемое «что будет создано», без секретов.

**TDD:** тесты пишутся первыми, `tests/api.provision-tenant.test.js`. Обязательные
случаи: пустая строка, битый JSON, домен с кириллицей, домен со слэшем, дубль домена в
списке, незнакомая вертикаль, неверная почта, PIN из пяти цифр, процедура с нулевой
длительностью, лишний ключ, валидная заявка целиком.
**Мутация:** снять проверку домена - падают именно доменные тесты, а не «что-нибудь».

**Гейты:** `node --test` (715 + новые), `node --check`.

## Фаза 2. Заведение в базе, одной транзакцией

**Файлы:** `api/lib/provision-tenant.js` (+ `provisionTenant`), `api/server.mjs`
(вызов в `startServer` после `runMigrations`, до `listen`).

- поиск по доменам заявки → найден: выход без записи, лог «уже подключён, id=N»;
- `INSERT INTO tenants` → id;
- `INSERT INTO staff`: роль `owner`, `must_change_pin = true`, `protected_owner = true`,
  `provides_services` из заявки, **явный `tenant_id`** (в служебном контексте умолчание
  колонки `current_setting('app.tenant_id')` равно `'*'` и вставка упала бы);
- `INSERT INTO services` × N + `INSERT INTO master_services` для владельца;
- в `/health` добавляется время старта процесса: без него нечем отличить
  перезапущенный контейнер от старого, а от этого зависит и снятие `NEW_TENANT`
  (шаг 7 фазы 6), и вся история с `BACKUP_TOKEN`. Одна строка, наружу уходит только
  метка времени;
- `clearTenantCache()` после успеха - иначе минуту живёт отрицательный ответ по домену;
- всё внутри одного `runInTenant(SYSTEM_TENANT, ...)`: ошибка → откат целиком;
- разбор заявки и её выполнение обёрнуты так, что **любая** ошибка логируется и
  сервер продолжает старт.

**TDD:** `tests/api.provision-tenant-db.test.js` на поддельном клиенте (тот же приём,
что `tests/api.tenant-context.test.js` с `__setBasePoolForTests`): порядок вставок,
явный `tenant_id` во всех, ранний выход при найденном домене, откат при сбое на
последней вставке, старт при битой заявке.
**Мутация:** убрать явный `tenant_id` из вставки staff - тест обязан упасть.

**Гейты:** `node --test`, `node --check`.

## Заранее продуманные грабли

- **Кэш справочника минута** - после заведения сбрасывается в коде; для проверки с
  машины помнить про `TENANT_CACHE_TTL_MS`.
- **CORS берётся из строки арендатора**: домена нет в списке - браузер даст невнятный
  отказ, а не понятную ошибку. Домен кабинета обязан лежать в `domains` с самого
  заведения.
- **Одинаковые почты у разных арендаторов - штатный случай** (ловушка 8 Этапа A). Ключ
  составной `(tenant_id, email)`. «Чинить» уникальностью почты нельзя.
- **Ответ уходит после фиксации транзакции** (`api/lib/http.js`).
- **Словарь нельзя звать при загрузке модуля** (находка Этапа B) - подпись застынет
  барбершопной, тесты класса `tests/vertical-lazy-labels.test.js`.
- **Гонка двух экземпляров приложения** при старте: заведение защищено уникальностью
  проверки внутри одной транзакции; если Amvera когда-нибудь поднимет второй
  экземпляр, повторный старт получит уже существующий домен и выйдет без записи.
- **Не заводить `NEW_TENANT` на постоянку**: переменная снимается после заведения,
  иначе каждый перезапуск будет молча пытаться завести клиента заново.
