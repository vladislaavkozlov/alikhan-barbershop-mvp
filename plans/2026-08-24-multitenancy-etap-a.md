## Challenge Log

### Q1. Решает ли проблему?

Каждый критерий приёмки спеки закрыт фазой:
критерии 1-3 → Фазы 1 и 3 · критерий 4 → Фаза 4 · критерии 5, 7 → Фаза 5 ·
критерий 6 → Фаза 2 (справочник) + Фаза 4 (домен).

### Q2. Самое ли эффективное решение? Три варианта

| | Подход | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **A** | Общая база + признак арендатора + RLS + контекст запроса | Замок в базе, а не в коде. **222 места с SQL не трогаются.** Тысячи арендаторов на одном сервере. Путь к отдельной базе для ВИП открыт без правок кода | Требует дисциплины с транзакциями, ловушки 1-3 из спеки | **выбран** |
| **B** | Отдельная база на каждого клиента | Физическая изоляция, миграция Алихана тривиальна | N баз обновлять и мониторить, дорого на клиента, не тянет тысячи, сквозная аналитика невозможна | отклонён как основной, оставлен как ВИП-опция позже |
| **C** | Признак арендатора + условие в каждом запросе руками | Дёшево на старте | 222 места, забытое условие = чужие пациенты. Это ровно тот класс ошибки, что уже случился 13.08.2026 с ролями | отклонён |

**Почему A дешевле, чем кажется.** Ключ - две вещи вместе:
`AsyncLocalStorage` (штатный модуль Node, без зависимостей) хранит соединение
текущего запроса, а `pool` подменяется прокси, который это соединение берёт. Плюс
`DEFAULT current_setting('app.tenant_id')` на колонке. В результате существующие
`pool.query('SELECT ... FROM bookings')` и `INSERT INTO bookings (...)` работают
без единой правки, а фильтрацию и проставление арендатора делает база.

**Подтверждение практикой (WebSearch 24.08.2026):** `SET LOCAL` в транзакции +
`FORCE ROW LEVEL SECURITY` + индекс с арендатором впереди - канонический паттерн,
одинаково описанный у Crunchy Data, AWS и в независимых разборах ловушек.

### Q3. Есть ли код ради кода?

Не входит: словарь вертикалей, флаги модулей, темы, биллинг, орто-модули. Всё это
Этапы B-D. Этап A - только изоляция. Попутный рефакторинг `crm-schedule-views.js`
и `mockup-crm.css` не трогаем, хотя руки тянутся.

### Q4. Общий контракт с несколькими потребителями?

**Да, в чистом виде** - слой доступа к базе и схема, на которые завязаны все 12
файлов роутов и три кабинета. По дисциплине Shared-Contract-First контракт идёт
отдельными фазами (1-3) и должен быть зелёным до фазы, где меняется поведение
входа и CORS (4). Фазы строго последовательны, параллелить нечего.

## Фаза 1. Контракт доступа к базе

Ветка `feature/tenant-context`. Фронтенд и схема не трогаются.

- `api/lib/tenant-context.js` - `AsyncLocalStorage`, `runInTenant(tenantId, fn)`,
  `currentTenantId()`
- `api/lib/db.js` - `pool` становится прокси: `.query()` и `.connect()` отдают
  соединение текущего запроса. Внутри `runInTenant` открывается транзакция и
  выполняется `SET LOCAL app.tenant_id`
- Вложенные `BEGIN` (10 мест в `bookings.js`/`schedule.js`/`staff.js`) переводятся
  на точки сохранения - поведение отката сохраняется, код роутов не переписывается
- Поток живых событий (`events.js`) и отдача медиа исключаются из обёртки: арендатор
  определяется, соединение сразу отпускается (ловушка 3)
- Запуск миграций получает служебный контекст `'*'`
- Запрос без арендатора **падает**, а не идёт на общий пул (fail-closed)

**Тесты (сначала красные):** утечка контекста между двумя запросами разных
арендаторов на одном соединении; запрос без арендатора отклонён; откат по точке
сохранения работает как раньше; поток событий не держит соединение.

**Гейт:** `node --check` по всем изменённым, `node --test` целиком зелёный.

## Фаза 2. Схема: справочник и признак принадлежности

Ветка `feature/tenant-schema`. Одна миграция `057_tenants.sql`, только схема.

- Таблица `tenants` (id, название, домены, вертикаль, статус) + строка «Алихан» = 1
- Во все 14 таблиц: `tenant_id integer NOT NULL DEFAULT 1 REFERENCES tenants(id)` -
  существующие строки достаются Алихану автоматически
- Вторым шагом внутри той же миграции: `SET DEFAULT current_setting('app.tenant_id')::int`
- Индексы с арендатором первой колонкой на всех таблицах, по которым идут выборки
  (ловушка 6)
- Составные уникальные ключи вместо глобальных (ловушка 5): `staff.email`,
  `clients(phone)`, `holidays.date`, `staff_one_protected_owner_idx`,
  `schedule_shifts(master_id, date)`, три dedup-индекса уведомлений
- Одиночные строки настроек становятся строкой на арендатора (ловушка 4):
  `payroll_settings`, `discount_settings`

**Тесты:** миграция накатывается на копию боевой базы без потери строк - счётчик
по каждой из 14 таблиц до и после совпадает; все существующие строки получили
арендатора 1.

**Гейт:** офлайн-набор зелёный, счётчики строк совпали.

## Фаза 3. Замок в базе

Ветка `feature/tenant-rls`. Миграция `058_rls.sql`.

- `ENABLE` **и** `FORCE ROW LEVEL SECURITY` на всех 14 таблицах (ловушка 1)
- Политика: строка видна, если её арендатор совпадает с контекстом запроса, либо
  контекст служебный `'*'` (только запуск миграций)
- Отдельно проверяется, что политика распространяется на запись и удаление, не
  только на чтение

**Тест-атака (главный тест этапа):** эфемерная база, два арендатора с данными;
из-под второго дёргаются все роуты; ни одна строка первого не возвращается. Тест
обязан **падать**, если `FORCE` убрать - иначе он ничего не проверяет.

**Гейт:** тест-атака зелёная и доказанно чувствительная.

## Фаза 4. Арендатор по домену

Ветка `feature/tenant-routing`.

- `tenants.domains` - список доменов арендатора
- Определение по заголовку запроса на входе сервера, до маршрутизации
- Неизвестный домен → 404 (критерий 4)
- CORS: разрешённый источник берётся из справочника вместо одной переменной
  окружения (ловушка 7)
- Вход: поиск сотрудника по паре арендатор + почта (ловушка 8)
- Сессия привязывается к арендатору; чужой токен на чужом домене не действует

**Тесты:** неизвестный домен даёт 404; токен арендатора 1 на домене арендатора 2
отклонён; два сотрудника с одинаковой почтой в разных арендаторах входят каждый
к себе.

**Гейт:** офлайн-набор зелёный + живой прогон логина через CDP.

## Фаза 5. Репетиция и переключение прода

Ветка не нужна, работа с базой и деплоем.

1. Снять копию боевой базы
2. Накатить миграции на копию, сверить счётчики строк
3. Живой CDP-прогон трёх кабинетов Алихана против копии - поведение как до
   (критерий 5)
4. Записать и проверить путь отката
5. **Предупредить Алихана** о коротком простое (видимое изменение для реальных
   пользователей)
6. Переключение прода - **только по явной команде Влада**
7. После деплоя: активная проверка вживую, наблюдение за логами 10 минут

## Риски и как ловим

| Риск | Как ловим |
|---|---|
| Транзакция на запрос исчерпает пул на медленных роутах | Фаза 1: поток событий и медиа исключены; замер удержания соединения на живом прогоне |
| Вложенные `BEGIN` сломают откат | Фаза 1: точки сохранения + тест на откат |
| Миграция уронит прод (был инцидент 04.08.2026) | Фаза 5: репетиция на копии до боевого запуска, откат готов |
| RLS замедлит выборки | Фаза 2: индексы с арендатором впереди; замер до/после на живом объёме |
| Ложноположительный тест изоляции | Фаза 3: тест обязан падать при снятии `FORCE` |
| Забытая таблица без арендатора | Фаза 3: проверка, что все 14 таблиц имеют и колонку, и политику - списком, а не глазами |

**Живая находка для Фазы 3.** После `COMMIT` Postgres возвращает сброшенной
настройке пустую строку, а не NULL. Это в нашу пользу: `''::int` падает, то есть
запрос без арендатора получает ошибку, а не «арендатор ноль». Политику писать с
учётом этого.

**Замеры для Фазы 5.** Транзакция на запрос удерживает соединение на всё время
обработчика. Два места, где это заметно: загрузка фото сотрудника (сжатие `sharp`
внутри запроса) и четыре роута с `Promise.all` нескольких запросов (аналитика,
зарплата, недополученная прибыль) - они теперь идут последовательно по одному
соединению. Ни то ни другое не меняет ответов, но время удержания меряем на живом
прогоне фазы 5.
