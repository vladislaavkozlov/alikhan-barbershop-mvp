## Что не так с server.mjs (из аудита)

Единственная функция-обработчик `const server = createServer(async (req, res) => {...})`
занимает **~1310 строк** (было: 1306-2617 на момент аудита) и содержит **27 инлайн-блоков
роутов** (`if (parts[0] === 'bookings' ...)`), в каждом вперемешку - валидация, SQL-запросы,
бизнес-правила, формирование ответа. Правка одного роута требует пролистать весь файл, потому
что чёткой структуры/файлового разделения нет - только комментарии-разделители `// ── ... ──`.

Домены естественно распадаются 1:1 с фичами фронтенда (реестр `const ROUTES = [...]` уже задаёт
эти границы, просто тела обработчиков не вынесены):

| Домен | Роуты | Прибл. объём |
|---|---|---|
| auth | `/auth/login`, `authenticate`, `requireRole`, `hashPin`/`verifyPin`/`createSession` | ~150 строк |
| staff/roles/portfolio | `/staff`, `/staff/:id/portfolio`, `/staff/:id/role` | ~82 строки |
| services/pricing | `/services`, `/master-services`, `/master-services/:masterId/:serviceId` | ~78 строк |
| bookings | `/bookings`, `/bookings/:id/cancel`, `/bookings/:id/status`, `/sales`, `createBookingTx`, `listBookingsForRequest` | ~430 строк |
| schedule (смены/график) | `/schedule`, `/schedule-range`, `/holidays`, `/schedule-availability`, `/masters-next-availability`, `/master-weekly-schedule` + `validateWeeklyChanges`/`writeWeeklySchedule`/`applyScheduleDay` | ~670 строк |
| schedule-requests | `/schedule-requests`, `.../decision`, `.../cancel` | ~325 строк |
| notifications | `/notifications` + `notifyStaff` | ~145 строк |
| payroll/finance | `/payroll-settings`, `/payroll`, `/revenue/today` | ~88 строк |
| clients | `/clients?risk=true`, `/clients/:id`, `/owner/alerts` | ~56 строк |

Плюс общая инфраструктура на вынос в `api/lib/`: `sendJson`/`readBody`/`setCors`/`matchRoute`
(http.js), `minutesToTime`/`addMinutes`/`addDaysIso`/`intervalsOverlap`/`shopNow` (time.js),
`pool`/`casWrite`/`runMigrations` (db.js).

**Целевая структура** (из аудита, не копировать имена механически - сверить с реальными
зависимками кода на момент старта):
```
api/
  server.mjs          # тонкий: HTTP-сервер, CORS, разбор запроса, диспатч по ROUTES
  routes/
    auth.js  staff.js  services.js  bookings.js  schedule.js
    schedule-requests.js  notifications.js  payroll.js  clients.js
  lib/
    http.js  db.js  time.js
  migrations/          # без изменений
```

## Как делать (методология Этапа 1 сработала - повторить один в один)

1. Скилл `вайбкодинг`.
2. Мини-план в `plans/` с точными доменами/границами (по образцу
   `plans/2026-08-07-crm-auth-decomposition.md`).
3. Живой verify-скрипт ДО первого переноса, подтвердить baseline GREEN на нетронутом коде
   (по образцу `tools/verify-refactor-crm-auth-decomposition.mjs`, но для бэкенда можно проще -
   роуты уже покрыты `tests/api.*.test.js`, 13 файлов, это сильная регрессионная сеть, которой
   не было у фронтенда).
4. По одному домену за раз, отдельный коммит, прогон после каждого: `node --check`,
   `node --test` (149 применимых + известный хвост `tests/api.roles.test.js` - см. ниже),
   живой прогон.
5. **Обязательно грепать ВСЕ callsites функции по всему файлу перед переносом, не только её
   определение** - в Этапе 1 ровно это дважды дало регрессию (пойманную живым прогоном, не
   `node --check`):
   - функция использовалась не только в перенесённом коде, но и напрямую в другом месте,
     которое ещё не переехало;
   - функция-потребитель была перенесена раньше функции-поставщика, импорт остался указывать
     на старый (уже неверный) источник вместо нового.
6. Циклические импорты между новыми `routes/*.js` и `server.mjs`/`lib/*.js` - это нормально и
   безопасно для ES-модулей, если используются только внутри тел функций, не на верхнем уровне
   модуля (подтверждено живьём в Этапе 1, использовалось многократно).

## Важные нюансы именно для бэкенда (не было в Этапе 1)

- **`tests/api.roles.test.js` уже красный ДО этого рефакторинга** (6 из ~19 тестов файла) -
  бьёт в реально задеплоенный прод Amvera (не в локальную БД), падает с `master_not_bookable`.
  Известный, задокументированный хвост, никак не связан со структурой кода. НО: раз Этап 2
  трогает именно backend-файл (в отличие от Этапа 1, где это было железно "не может быть
  связано"), после каждого переноса домена стоит явно перепроверить, что причина падения
  осталась ТОЙ ЖЕ (`master_not_bookable`), не появилась новая - чтобы не пропустить настоящую
  регрессию под видом уже известной.
- Деплой бэкенда на Amvera - отдельный репозиторий с ПЛОСКОЙ раскладкой (только `api/server.mjs`
  → `server.mjs` в корне того репо), см. `reference_amvera-deploy-gotchas.md` в памяти или
  прошлые деплои этого проекта (Окна 37/38) для точного паттерна копирования. Готовность ловить
  не по `/health` (лжёт до пересборки), а по переходу конкретного роута с 404 на реальный
  ответ - тот же приём, что уже использовался.
- Деплой backend = risk выше, чем у Этапа 1 (реальные деньги за поминутный тариф Amvera,
  реальный прод-трафик) - как и раньше, деплою только по явной команде Влада, порядок
  бэкенд→фронт при совместных изменениях.

## С чего начать в новом окне

1. Прочитать этот файл целиком.
2. Прочитать `plans/2026-08-07-crm-auth-decomposition.md` как образец методологии и формата.
3. Сверить актуальные номера строк в `api/server.mjs` (могли сдвинуться со времени этой
   заметки) - `grep -n "^async function \|^function \|^const ROUTES" api/server.mjs`.
4. Написать новый план `plans/<дата>-server-mjs-decomposition.md` по тому же формату.
5. Дальше - по методологии выше, домен за доменом.
