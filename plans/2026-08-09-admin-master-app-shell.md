**СТАТУС: ЗАКРЫТО 09.08.2026.** Все 3 фазы реализованы и закоммичены локально (`a57a8e4`
Окно 47, `02db3a7` Окно 49, `a3f552d` Окно 50). 40/40 живых CDP-проверок зелёные (11 - Окно 47,
14 - Окно 49, 15 - Окно 50, включая regression Owner+Admin+Master в каждой последующей фазе).
Деплой НЕ делался - только по отдельной явной команде (правило проекта).
**Размер: M.** Почему: 3 фазы, трогает общий файл (`assets/crm-app-shell.js`), у которого уже

потребители разносятся по разным фазам, поэтому больше 1-2 файлов и больше одной сессии.

## Проблема (из разбора этой сессии, код проверен напрямую, не по памяти)

У Owner (`crm-owner.html`) с Окна 41 стоит премиальный sidebar (220px, сворачиваемый до иконок,
общие design tokens `assets/mockup-crm.css`) - постоянная левая панель вместо старой
горизонтальной `.tab-bar`. У Admin (`crm-admin.html`, 2 вкладки: Расписание/Сотрудники) и
Master (`crm-master.html`, 3 вкладки: Мой день/Моя зарплата/Личные данные) sidebar нет вообще -
обе страницы всё ещё на старой мобильной `.tab-bar` (radio `pt-a`/`pt-b`/...), визуально из
другой эпохи продукта относительно Owner.

Задача - подключить тот же sidebar-механизм к Admin и Master, тем же стилем, что у Owner,
без изменения содержимого их существующих панелей и без регресса на все три страницы.

## Challenge Log

**Chosen solution:** параметризовать существующий `assets/crm-app-shell.js` (сейчас
захардкожен под 5 разделов Owner) - вынести конфиг в объект `ROLE_CONFIG['owner'|'admin'|'master']`,
`initAppShell(role)` берёт нужный набор разделов/иконок/подписей по роли. Admin/Master просто
подключают тот же файл и вызывают `initAppShell('admin')`/`initAppShell('master')`.

**Alternatives considered:**
1. Скопировать `crm-app-shell.js` в 2 отдельных файла под Admin/Master - отклонено: три копии
   одного и того же механизма (сворачивание, анимация, роутинг). Уже был прецедент в этом же
   проекте (Окно 46, "почему анимация обновления только в Уведомлениях") - несинхронные копии
   логики расходятся при первом же будущем фиксе.
2. Генерировать sidebar из data-атрибутов в HTML вместо JS-конфига - отклонено: `insertSidebar()`
   и так строит DOM в JS, парсинг HTML-атрибутов обратно в тот же формат - лишний слой, не проще.
3. Параметризация одного файла (выбрано) - один механизм, один источник правды на анимации/
   сворачивание/роутинг, конфиг - единственное, что различается по ролям.

**Почему выбранное решение лучше:** механизм (`toggleSidebar`, `insertToggleButton`,
`goToSection`, вся CSS-анимация в `crm-app-shell.css`) уже написан, проверен, прошёл 3 раунда
живой полировки под Owner (см. `plans/archive` историю Окна 41-46) - переиспользовать его, не
писать заново. CSS-файл (`crm-app-shell.css`) уже role-agnostic (комментарий в самом файле:
"безопасен для них по построению" - там нет ни одной привязки к Owner), под него менять ничего
не нужно.
