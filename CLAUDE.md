# barbershop-alikhan-mvp - карта проекта

CRM + публичный сайт записи для барбершопа "Алихан" (Ставрополь, 2 точки). Реальный клиент,
реальные деньги, прод. Разработка идёт скиллом `вайбкодинг` через пронумерованные "окна"
(один промпт = одна фича/фикс). Реестр всех окон - [WINDOWS-INDEX.md](WINDOWS-INDEX.md), не
пересказывается сюда.

## Где что лежит

- **GitHub Pages** (фронтенд) - `git push origin main`, обычный git-репозиторий этого проекта

  своя история, деплой = копирование `server.mjs`+`lib/`+`routes/`+`migrations/` в клон и пуш в `master`.
  Гочи и точный процесс - память `reference_amvera-deploy-gotchas.md`

## Легаси-долг (явные границы, не трогать мимоходом)

- **`assets/mockup-crm.js`** - classic `<script>` (не ES-модуль), подключён напрямую во все 3 CRM-страницы
  параллельно с `<script type="module">`. Держит виджеты даты/времени (`toggleCustomSelect`/
  `toggleCustomDate` через `onclick=`) и `updateNoShowUi()` - HTML `onclick` резолвится только через
  глобальный `window`, это ограничение браузера, не архитектурная небрежность. **Осознанно оставлено
  как есть** при декомпозиции `crm-auth.js` (Этап 1, 07.08.2026) - миграция потребовала бы смены модели
  виджетов, это отдельное окно, не побочный эффект рефакторинга. Не трогать попутно с другими задачами.
- **`assets/mockup-crm.css`** (монолитный legacy stylesheet, ~1000 строк) - design tokens текущего
  редизайна владельца (Окно 41+) едут в отдельные файлы (`assets/crm-app-shell.css`), не сюда. При
  добавлении новых токенов - в новый файл, не в монолит.
- **`assets/crm-schedule-views.js`** (крупнейший фронтенд-файл, ~760 строк) - в плане Этапа 1
  декомпозиции был по ошибке отнесён к "уже маленьким" и исключён из переноса; на 07.08.2026 это
  утверждение уже неверно. Кандидат №1 на декомпозицию тем же методом, что и `crm-auth.js`
  (см. `plans/archive/`).

## Правило: QA-фикстуры НЕ через миграции

04.08.2026 миграция `031_cleanup_qa_window19.sql` уронила прод на ~20 минут - `DELETE FROM staff`
упал на непредусмотренном FK (`schedule_change_requests`), а упавшая миграция валит весь сервер (503
на всех роутах, не только новом). С тех пор в `api/migrations/` продолжает расти пара "create QA
account for window N" → "cleanup QA account for window N" (023↔024, 025↔027, 028↔035, 029↔031,
038↔039) - каждая такая пара это лишний риск повторить тот же инцидент и лишний шум в истории схемы.

**Правило:** миграции - только про schema (таблицы/колонки/индексы/constraints), никогда про
временные тестовые данные для CDP-прогона конкретного окна. QA-фикстуры создавать и чистить внутри
самого verify-скрипта (`tools/verify-*.mjs`) через прямые SQL-вызовы или API-логин на эфемерной
тестовой базе - тот же паттерн, что уже используют `tools/verify-2026-08-*-okno*.mjs` для остальных
проверок. Если нужен guaranteed-clean QA-аккаунт на самом проде - это одноразовое ручное действие
по явной команде, не отдельная миграция в постоянной истории схемы.

## Общие правила разработки (из практики проекта)

1. Декомпозиция большого файла - по одному домену за раз, отдельный коммит на каждый, прогон
   `node --check` + офлайн-тесты + живой CDP после каждой фазы (образец - `plans/archive/`)
2. Поведение/API-контракты при структурном рефакторинге не меняются - код переносится, не переписывается
3. Честная поправка к ТЗ лучше, чем выдуманная реализация - если промпт разошёлся с реальным кодом
   (устаревший файл, отсутствующий UI-элемент), фиксировать поправку явно, не подгонять факт под текст
4. security-review - перед каждым коммитом с новым пользовательским вводом
